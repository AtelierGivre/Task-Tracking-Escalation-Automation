# Recurring Task Tracker — Allo Innoware assignment

A Google Sheets + Apps Script prototype that answers one question for the team every morning:
**who owes what today, and who has already been chased?**

The sheet is the operating interface. Apps Script supplies the dates, the completion log,
the manager alert and the leadership escalation. Nothing depends on someone remembering to
open a tab.

---

## 1. Workbook tabs

| Tab | Purpose | Edited by |
|---|---|---|
| **Read Me** | One-page operating guide, generated by the script | script |
| **Employee View** | One row per task. Employee pastes the Ticket ID in column G or ticks column H. Everything else is a live `FILTER` of `Tasks`. | employee (G, H only) |
| **Pending Now** | Only the rows that are Overdue or Due today, sorted by employee then date | script |
| **Manager** | Every task with its next due date, status and an acknowledgement dropdown | manager (F only) |
| **Manager Alerts** | Audit trail: one row per alert, acknowledgement timestamp, escalation timestamp | script |
| **Tasks** | Master: task, owner, frequency, type, ticket required, last completed, next due, status formula | admin |
| **Completion Log** | One row per completed cycle (who, when, proof / Ticket ID, cycle due date) | script |
| **Correction History** | Only written when a proof is corrected (max 2 per cycle) | script |
| **Test Log** | PASS/FAIL evidence for Tests 1–8 | script |

The employee never types into `Tasks` or `Completion Log`. That is how duplicate work is
removed: the report they read is the report they update.

## 2. Recurring cycle logic

- Each task stores `Frequency (Days)`: 1, 7, 15 or 30.
- On completion the script writes `Last Completed = now` and
  `Next Due = now + Frequency`. The employee never calculates a date.
- `Status` is a per-row formula: `Overdue` when `Next Due < TODAY()`, `Due today` when equal,
  otherwise `Scheduled`. It is never written by the script, so it can never go stale.
- A cycle is identified by **Task ID + cycle due date**. That key is what stops the same cycle
  being logged twice, alerted twice or escalated twice.

Why completion-based rather than calendar-anchored: if a 7-day task is finished a day late, the
next one is still a full 7 days away, so nobody is immediately overdue for a task they only just
did. A calendar-anchored variant (due date + frequency) is a one-line change if the business
prefers fixed slots.

## 3. Daily task method (no ticket ID)

Requirement: prove a WhatsApp update happened without adding admin work.

Design: **checkbox + automatic proof text.**

1. Employee posts the update in the group as usual (nothing new).
2. In `Employee View`, they tick column H on their daily row.
3. The script writes a `Completion Log` row with `Completed By`, exact timestamp and
   `Proof / Ticket ID = "WhatsApp update"`.
4. Optionally they can type a reference in G before ticking (`"09:15 posted"`), which is stored
   as the proof instead of the default text.

Why this shape: a daily task repeats 20+ times a month, so anything longer than one click stops
being used. One click is auditable (who/when), needs no portal, and keeps the same operating tab
as the ticket tasks. If the group is later replaced by a portal, the same row simply starts
accepting a Ticket ID.

## 4. SLA design (Test 7 reasoning)

| Step | Timing | Why |
|---|---|---|
| Task due | **18:00** local time on the due date (`DUE_HOUR`) | End of the working day: the employee has had the whole day, and the alert still lands on the due date, not the morning after. |
| Manager alert | First hourly run at or after 18:00 | Same-day alert as the brief requires. Hourly, not per-minute, keeps the run cheap and the mail volume predictable. |
| Manager acknowledgement | Any time after the alert | Captured with a timestamp so "I never saw it" is answerable. |
| Leadership escalation | **4 hours after the alert**, if the task is still not completed | Enough time to chase a person in the evening/next morning, without letting a genuine miss sit for a day. Acknowledging the alert does **not** stop the escalation: the work is still undone, which is exactly what leadership needs to know. |
| Repeat emails | None for the same task + cycle | Dedupe key = Task ID + cycle due date for alerts; a single `Escalated` flag for escalations. |

Acknowledging closes the loop for the manager; only a completion closes the task. The system
therefore knows two different things: *did the manager review it* and *was the work done*.

Tunables, top of `Code.gs`: `DUE_HOUR`, `ESCALATION_HOURS`, `MAX_CORRECTIONS`,
`MANAGER_EMAIL`, `LEADERSHIP_EMAIL`, `SEND_EMAILS`.

## 5. What was tested (Tests 1–8)

`Allo Ops > Run all tests` runs the scenarios against throwaway `T-TEST*` rows, writes
PASS/FAIL to **Test Log**, then deletes the throwaway rows. It sends real emails while it runs;
that is deliberate, since delivery is part of the claim.

| Test | Scenario | Where to look |
|---|---|---|
| 1 | Complete a 7-day task → next cycle is 7 days out automatically | `Test Log`; `Tasks!G:H` |
| 2 | One completion entry, one log row, no second update | `Test Log`; `Completion Log` |
| 3 | Daily task completed with no ticket ID | `Test Log`; proof = `WhatsApp update 09:15` |
| 4 | Overdue task → manager alert row + email | `Manager Alerts`; mailbox |
| 5 | Manager acknowledgement → status + timestamp | `Manager Alerts!F,H` |
| 6 | Unresolved past SLA → escalation email, `Escalated` flag | `Manager Alerts!G,I`; mailbox |
| 7 | Fresh alert → **no** escalation before 4 hours | `Test Log` (expected blank) |
| 8 | Three consecutive runs → no duplicate alert, log or email | `Test Log`; row counts unchanged |

Manual demo of the same flow is in `SETUP.md`.

## 7. Limits / next hardening

- Google consumer accounts cap `MailApp` at ~100 recipients/day. Fine for 3–4 people; for a
  larger team, send from a Workspace account or batch one digest per manager.
- `Employee View` is one tab for everyone, filterable by name. At 10+ people, split per-employee
  filtered views or protect rows (the brief's 3–4 people do not need it).
- Corrections are capped at 2 per cycle and recorded in `Correction History`, so a changed
  Ticket ID is visible rather than silent.
- Alerts fire at 18:00 in the spreadsheet timezone (File → Settings). The script reads the sheet
  timezone, so it cannot drift from the `TODAY()` used by the status formula.
- If the script is ever re-run, existing alerts/logs are keyed so no duplicates are created; the
  only destructive command is `Reset demo data`, which is meant for demos.
